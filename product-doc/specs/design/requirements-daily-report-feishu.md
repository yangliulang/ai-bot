# 产品视角 · 需求与范围日报（飞书群推送 · 设计方案）

## 文档定位

- **读者**：产品负责人、项目组干系人、需同步「昨天规格/范围上发生了什么」的业务方（**不是**研发看 commit 的工具说明）。
- **承诺**：每天在固定时间推送 **一份可读的产品日报** —— 回答「对用户/交付有什么含义」，而不是罗列文件路径与技术合并记录。
- **渠道**：飞书群 + 自定义机器人（Webhook）；正文用 **叙述 + 列表**，避免群里出现「得像看 Git 才知道在说什么」的内容。

---

## 1. 背景与目标

- **背景**：本仓库的需求与范围真源主要在 `specs/requirements/`，辅以 `product/` 的产品叙事。团队希望在群里 **低负担地对齐**：昨天在「需求与范围」层面推进了什么、有没有拍板或待决策。
- **目标**：
  - 固定节奏发布 **产品向日报**（结论优先、短句、可转发）；
  - **无实质进展时** 也要有明确话术（例如「本日无新增范围变更说明」），避免沉默被误判为机器人故障；
  - 文末可提供 **可选**「深度链接」给需要查原文同学（链接到文档或 PR，而非把路径当正文主体）。

---

## 2. 非目标（首期不做）

- **不替代** 契约收口与 DoD（见 [`contract-closure.md`](../requirements/contract-closure.md)、[`closure-remaining.md`](../requirements/closure-remaining.md) 的专职流程）；日报只 **播报与对齐**，不自动关单、不改矩阵状态。
- **不把技术实现细节写进群发正文**：例如 commit hash、`git` 命令、目录树级别的「改了哪些 `.md` 文件清单」不作为主叙事（若运维需要，见 **附录 A**）。
- **不默认覆盖纯代码改动**（`src/**`）；若某日只有实现无规格变更，产品日报应以 **「无范围文档更新」或「详见发布说明」** 为准，或由负责人在模版里手写「已对用户的可见变化」（若有灰度）。
- **不做群内 @ 机器人问答**（需要时二期再上企业自建应用）。

---

## 3. 信息怎么来（产品上可理解的链路）

规格与叙事仍写在仓库里；**日报内容由人最终把关**，可选半自动线索辅助（摘要候选、变更文件提示），避免出现「全文 diff」或泄密风险。

```mermaid
flowchart LR
  SSOT[规格与产品叙事仓库]
  Draft[简报草稿或候选摘要]
  Human[Owner 按模版润色拍板]
  Feishu[飞书群消息]
  SSOT --> Draft --> Human --> Feishu
```

| 环节 | 产品向说明 |
|------|------------|
| **素材来源** | 前一日实际合并进主干（或约定分支）的 **范围类叙事变更**：产品叙事、域需求、主流程、收口类文档等（与 [workspace-layout](../../.specify/memory/workspace-layout.md) 中的 `specs/requirements/`、`product/` 对齐）。 |
| **Draft** | 可由工具从「变更线索」生成 **候选要点**（例如 PR 标题、提交说明中的产品语言）；**不得**未经审核直接当对外口径。 |
| **Human** | 指定 **产品日报 Owner**（轮值或固定），用第 4 节日模版在 5～10 分钟内定稿；无变更则勾「无范围变更」固定短讯。 |
| **Feishu** | 定稿后推送；样式用 **文字 + 简单分节** 即可，后续可换卡片仅影响版式不改变信息架构。 |

---

## 4. 飞书消息结构（产品日报模版 · 建议）

**标题行（一行）**  
`【产品日报】YYYY-MM-DD（范围/需求侧）`

**1）今日结论（2～4 条 bullet）**  
- 用 **业务语言**：例如「Agent 账单 H5 补全了 xx 场景下的空态与错误口径」「关单路径上 closure 文档更新了 7.5 节执行勾选项说明」。  
- 避免：「合并了 3 个 PR」「改了 5 个 md」。

**2）范围与优先级**  
- **新增 / 扩大**：本日是否新增强承诺、新场景、新外部依赖。  
- **收缩 / 冻结**：是否明确「不做」「暂缓」「下期」。

**3）对用户或交付的影响（若有）**  
- 可见行为、合规披露、需要运营/客服同步的文案；没有则写「无用户侧可见变更说明」。

**4）里程碑与收口（若有）**  
- 与 roadmap / 里程碑、contract-closure 相关的 **产品侧** 进展一句话（不展开 DoD 表格）。

**5）阻塞与待决策**  
- 需要谁、在什么时间前拍板；没有则写「无」。

**6）延伸阅读（可选，小字或附在末尾）**  
- 1～3 个链接：`product/` 或关键 spec 的仓库链接、或当天合并说明（PR）；**勿**在正文堆文件路径。

**无变更日（固定短讯示例）**  
`【产品日报】YYYY-MM-DD：需求与范围文档侧无新增合并说明；用户侧无同步事项。`

## 5. 角色与节奏

| 角色 | 职责 |
|------|------|
| **产品日报 Owner** | 按模版定稿、对口径负责；可轮值。 |
| **研发/规格贡献者** | PR 标题与描述尽量带 **产品可读摘要**，减轻 Owner rewrite 成本。 |
| **工具维护（可选）** | 仅保证定时提醒、候选摘要、Webhook 可用；不替代 Owner 审阅。 |

**节奏**：工作日每日一次（或隔日 + 周一汇总），时区全团队统一（建议 `Asia/Shanghai`）；节假日可配置「跳过」或「仅发无变更短讯」。

---

## 6. 验收标准（产品向 DoD）

- 群消息在 1 分钟内能读懂 **「昨天范围上发生了什么」**，**不依赖** Git 知识。  
- 有变更日：**结论段** 非空且为业务语言；无变更日：**固定短讯** 出现。  
- 不在群发正文用 **文件路径列表** 代替产品结论（附录式链接除外）。  
- 飞书投递失败时有 **可观测告警**（由实现侧满足，见附录 A）。

---

## 7. 演进路线（仍按产品价值排序）

| 阶段 | 产品价值 |
|------|----------|
| **MVP** | 固定模版 + Owner 人工粘贴/半自动填充 + Webhook 推送 |
| **V1** | PR 标题自动汇总为「候选结论」、飞书卡片版式、@ 当日值班 |
| **V2** | 与里程碑/roadmap 条目弱关联（例如自动提示「本条是否影响 Qx 里程碑」） |
| **V3** | 群内可查历史日报（需自建应用能力与留存策略） |

## 附录 A：技术落地参考（运维/研发；非群发正文）

以下仅供实现「定时 + 投递 + 可选变更线索」，**不改变第 4 节的产品模版要求**。

- **变更线索数据源**：在时间窗内对约定路径（如 `specs/requirements/`、`product/`）做只读 Git 历史，生成 **候选清单**（提交说明、触及文件列表），仅供 Owner 审稿，不作为最终对外口径。  
- **投递**：飞书自定义机器人 Webhook + 签名校验；Secrets 不进仓库；失败重试。  
- **调度**：GitHub Actions `schedule`、cron 或云函数任选；需统一时区与统计引用分支。  
- **实现与运维说明（本仓库）**：本地调度 + Webhook — [scripts/product-daily-brief/README.md](../../scripts/product-daily-brief/README.md)（cron / launchd，`feishu.env`）。
