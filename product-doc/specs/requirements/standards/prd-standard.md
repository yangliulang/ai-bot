# 需求文档（PRD）书写规范

**适用**：向 **`specs/requirements/`** 增补或修订 **产品向、可对测试归因** 的需求正文（域文档、`product.md` 方向修订）。  
**不适用**：接口 PATH、库表、组件实现细节 — 写入 **`specs/design/`**。

---
**关单余量（MR 首节）**：[`closure-remaining` §0](../closure-remaining.md#closure-remaining-quicklinks) · [§6 / §6.4](../closure-remaining.md#cc-exec-solve-path)（[**§6.4 问题→动作**](../closure-remaining.md#cc-problem-to-action)）；**主契约** [`contract-closure`](../contract-closure.md)。

## 1. 文档定位与存放

| 内容类型 | 存放位置 | 说明 |
|----------|-----------|------|
| 方向、范围、非目标（仲裁） | [`product.md`](../product.md) | 范围表、术语简表；与域文档冲突时 **先改 specs 再回写** [`product/`](../../../product/README.md) |
| 按主题的功能需求与验收 | [`domains/*.md`](../domains/) | **FR / SC / US** 主战场 |
| 人类可读故事线 | [`../../../product/`](../../../product/README.md) | **不设** FR 编号；不写契约替代品 |
| 主流程步骤（业务级） | [`flows/`](../flows/) | 见 [`business-process-standard.md`](business-process-standard.md) |
| 渠道必选能力 | [`domains/agent/telegram/overview.md`](../domains/agent/telegram/overview.md)（**条文 SSOT**）；[`README.md`](../domains/agent/telegram/README.md)（**目录索引**） | 见 [`interaction-flow-standard.md`](interaction-flow-standard.md)；类型 A 字段下限 **`overview` §2.5.x** |
| 何时算「可对外承诺」 | [`contract-closure.md`](../contract-closure.md) | PRD 不得绕过矩阵 **`TBD`** 口径 |

**拆分原则**：同一主题下若 **步骤链跨 ≥2 个系统或 ≥2 个域** 且常被引用 — 用 **`flows/`** 收敛叙事；若 **仅会话形态与字段** — 用 **`domains/agent/telegram/`**；**规则与验收** 始终在 **`domains/`** 保留可追溯条文。

---

## 2. 文首元数据（推荐）

域级或重大切片建议在正文前使用 **固定表头**（字段示例如下，可按域裁剪）：

| 项 | 必填 | 说明 |
|----|------|------|
| 产品 / 特性名 | 是 | 与 `product.md` 一致 |
| 文档路径 | 是 | 仓库内相对路径 |
| 状态 | 是 | 草案 / 评审中 / 已冻结 等（用语可与 [`review-and-change-standard.md`](review-and-change-standard.md) §1 对齐） |
| 策略或一句话摘要 | 视域而定 | 计费、门禁、编排类域建议填写 |
| 互引 | 是 | 列出权威邻域文档及 **易混同名章节**（注明文件名 + §，避免串号） |

## 3. 建议章节结构

### 3.1 `domains/*.md`（域需求）

可按域裁剪，但 **不建议省略** 下列逻辑块：

| 顺序 | 章节 | 要点 |
|------|------|------|
| 0 | **目录**（长文） | § 与主题对照表，便于评审跳转 |
| 1 | **目的与范围** | **包含 / 不包含**；显式对齐 `product.md` **非目标** |
| 2 | **术语表** | 跨文档歧义项 **在权威域定义**；见 **§5**「术语权威」 |
| 3 | **与关联域的权威边界** | 表格：**主题 → 权威文档 → 本文职责** |
| 4 | **用户故事（可选）** | `US-xxx`，括号标注 **FR-xx** |
| 5 | **功能需求** | **FR 总览表** + **分条详述**（见 §4 模板） |
| 6 | **验收 / SC** | 可判定条文；可与 FR 同章或分立 |
| 7 | **开放决策 / 假设与依赖** | **D-n**、默认假设、依赖 **所内 PRD / `design/api`** |

### 3.2 `product.md`（方向级，短文）

不宜承载长篇 FR。建议稳定包含：**方向要点列表**、**范围表（包含项 + 说明列链向域/流程）**、**非目标**、**术语（简）**；重大变更时 **动机一句** 写入 MR 或变更摘要。

---

## 4. FR / SC 条目模板

### 4.1 功能需求（FR）

每条 **FR-xx** 建议具备下列要素（可用小节或加粗句，不必死板）：

- **触发**：谁在什么状态下发起（用户 / 系统 / 定时 / Webhook）。  
- **行为**：系统 **必须** 做什么（含关键字段语义，**不含** JSON Schema）。  
- **边界**：失败、超时、权限不足、余额不足等 **可见语义与阻断级别**（文案细则可指 **`domains/agent/telegram/`**）。  
- **追溯**：关联 **`flows/`** 步骤号、`scenarioId` / **`skillId`/`toolId`**（业务侧命名）、**设计文档**中能力是否已登记（仅引用，不抄 PATH）。  
- **验收**：指向 **SC-xx** 或本条下列 bullet。

### 4.2 成功标准（SC）

- **可度量**：含 **观测对象 + 条件 + 期望**。  
- **可归因**：若依赖外部系统 **不可判定态**，须与 **`design/architecture`** 等产品设计文档口径一致，不在 PRD 自创技术解法。

### 4.3 FR 与 SC 的对应关系

| 模式 | 用法 |
|------|------|
| **一对一** | 单条 FR 末写「验收：SC-xx」 |
| **多对一** | 若干 FR 共用同一 SC；SC 条下列出覆盖的 FR-xx |
| **仅 FR 内嵌 bullet** | 简单域可在 FR 下直接列验收点，不强行拆 SC — 但须 **仍可被 QA 执行判定** |

### 4.4 `product.md` 变更（方向级）

修改范围或非目标时建议最小包含：**动机一句 → 包含/不含对照 → 指向承接域文档路径**，避免只在 `product.md` 展开长篇 FR。

## 5. 编号与可追溯

| 类型 | 约定 |
|------|------|
| **FR** | **域内前缀 + 序号唯一**。前缀通常对应域缩写（单字母如 `FR-B`，或多字母如 `FR-TS`）；**新开域时** 在域内 **首次 FR 总览表脚注** 声明前缀，**禁止跨域复用同一 FR 编号**。 |
| **SC** | 与验收绑定；建议与同域 FR **前缀一致**（如 `SC-B`）或沿用团队统一的观测类编号 |
| **US** | 用户故事；映射到 FR |
| **D-n** | 开放决策；关闭后移到「已采纳」或在正文改写并保留脚注日期 |
| **§** | 章节号；**跨文档引用必须写文件名**（防同名章节串号） |

**术语权威**：若某词在多域有不同含义 — **选一域术语表为权威**，其他文档 **只引用文件名 + §**，不在正文重新定义冲突含义。**尚无独立术语表时**：至少在 **权威边界表** 或 **本条 FR** 首次出现处加脚注「定义见 …」。

**与设计文档分工**：`scenarioId`、`toolId`、`skillId`、矩阵 **`W`/类型 A** — PRD 写 **业务语义与门禁**；PATH / OpenAPI — 仅以 **`design/api.md`** 为准。

---

## 6. PRD 质量门禁（自检）

- [ ] **非目标**在 `product.md` 或本文「不包含」中可追溯，无隐含扩容  
- [ ] 每条 **FR** 具备 **触发 + 行为 + 边界**（或明确指向 **`flows` / `domains/agent/telegram`** 步骤）  
- [ ] **验收/SC** 可被 QA **执行判定**  
- [ ] **权威边界表**列出与本域存在 **数据流、权限、计费、渠道或配置交界** 的主题（不限于固定清单，**须穷尽本域真实依赖**）  
- [ ] **未编造**矩阵未冻结能力；**TBD** 与 [`contract-closure.md`](../contract-closure.md) **P0/P1** 叙述一致  
- [ ] 修改 FR 后 **flows/README、spec.md、`domains/agent/telegram/README`** 等索引是否需要联动已检查  
- [ ] 大块改动 MR **按需**填写 [`review-and-change-standard.md`](review-and-change-standard.md) **§3 变更摘要**

---

## 7. 反模式（避免）

| 反模式 | 建议 |
|--------|------|
| 在 `domains/` 长篇粘贴 **接口 JSON / SQL** | 改为 **`design/api.md`** 或 ADR |
| 同一规则在 **多域重复粘贴且不标注权威** | 选一域 **权威**，其余 **一行引用** |
| **仅有叙事无 FR/SC** | 叙事留在 **`product/`**；契约条目下沉 **`domains/`** |
| **FR 混入「建议实现」**（队列选型、缓存策略） | 迁至 **`design/`** 或非正式 RFC |
| **章节编号与他人文档同名不同义** | 表头 **互引** + 「本章 §x.x 专指 …」 |
| **大范围改 FR 但 MR 无摘要** | 使用 [`review-and-change-standard.md`](review-and-change-standard.md) **§3** |
| **在未声明前提下静默扩张范围**（正文新增能力却无配套 FR/非目标/收口核对） | 视为缺陷，须补 FR 或回写「不包含」 |

---

## 8. 对外承诺与设计契约对齐

凡描述 **对用户或合作方承诺的能力**（尤其 **交易所写、计费扣减、导出、自动化触发**）：须能在 **`design/api.md`** 矩阵或 [`contract-closure.md`](../contract-closure.md) 闭环中找到 **收口条件或已登记的 TBD 缺口**。

禁止 **仅在 `product/`、交互稿或外部 Wiki** 写「已支持 / 已上线」，而与 **`design/api` 矩阵 `TBD`** 长期矛盾。

## 9. 文档生命周期与元数据扩展（可选）

| 字段 | 用途 |
|------|------|
| **最近评审日期** | 大范围改写后记一笔；非强制 |
| **Owner / 对接角色** | 评审问起口人 |
| **外部追溯** | 大块变更关联 MR / Issue 编号 |

与 [`review-and-change-standard.md`](review-and-change-standard.md) **§1 文档状态**配合使用。

## 10. FR 依赖与非功能需求（NFR）落点

**FR 间依赖**：若某 FR **必须以另一条 FR 为前提**，在从属条目中写明 **「依赖 FR-xx」**，或在域内单独 **「FR 依赖 / 矩阵」**小节维护（保持单行可追溯即可）。

| NFR 主题 | 需求侧写什么 | 深度展开在哪 |
|----------|----------------|----------------|
| **日志 / trace / 脱敏 / UNKNOWN** | **SC** 一句 + 指向观测域文档（若仓库已拆分） | `domains` + **`design/architecture`** |
| **权限 / RBAC / 导出审计** | **FR**：谁能做什么、审计要什么 | 对应业务域 + **`design`** 若有契约 |
| **数据留存 / 导出合规** | **FR/SC**：保存时长、可申请主体 | 不写存储选型 |
| **可用性 / 延迟（若对用户承诺）** | **SC**：可验收口径 | **`design/`** 或 ADR |

**配置 Key**：若组织存在 **集中配置登记**（如运营台 Key），新 **`configKey`/枚举** 须在登记表与 MR **摘要中点名**。若本特性 **无任何全局配置**，无须捏造 Key —— 在 FR 中直接描述 **行为与可见参数** 即可。
